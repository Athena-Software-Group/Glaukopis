\begin{abstract}
Vulnerability response in security operations is a chain of mapping decisions: a newly disclosed CVE must be scored for severity and exploitability, traced to its weakness class and the adversary techniques it enables, and linked to mitigations and detections before a patch or compensating control is scheduled. Because the asset and exposure context behind these decisions often cannot leave the organization, locally served small language models (SLMs)---here, open-weight models of 8B to 32B parameters that a two-GPU host can fine-tune and serve---are attractive, but only if their outputs land on the correct catalog identifier and their training targets are traceable to source intelligence. We present an SLM specialization workflow built on a versioned Neo4j graph joining twelve public threat and vulnerability intelligence sources (e.g., NVD, CISA KEV, EPSS, CWE, ATT\&CK) (\emph{Ariadne}), and a template engine that materializes each instruction target by executing a typed graph query (\emph{Sophia}). Using a functionally optimized approach, we use a layered Instruction Fine-Tuning (IFT) template-based strategy to train Qwen2.5-32B-Instruct by which we increase attack-technique extraction scores from 18.2 to 65.8, vulnerability mitigation selection scores from 7.6 to 62.5, and the three-benchmark mean we use for testing from 57.7 to 65.0 (95\% bootstrap interval 64.1--66.0), with an 11.6-point decrease on the MMLU-Pro general-knowledge benchmark. Against the single-stage model that the first layer produces, the three later layers add 3.2 points to the three-benchmark mean but cost 2.3 points on the task-aligned benchmark.
\end{abstract}

\section{Introduction}
For each newly disclosed vulnerability (a Common Vulnerabilities and Exposures entry, CVE~\cite{cve}) found in a scan of a given environment, security operations center (SOC) analysts must join cyber threat intelligence (CTI) from separate, largely public catalogs: the CVSS severity vector from the National Vulnerability Database (NVD)~\cite{nvd}, exploitation likelihood from the Exploit Prediction Scoring System (EPSS)~\cite{jacobs2021epss}, confirmed exploitation from the CISA Known Exploited Vulnerabilities (KEV) catalog~\cite{cisakev}, public exploit code~\cite{exploitdb,pocingithub}, the weakness class (CWE~\cite{cwe}) and attack patterns (CAPEC~\cite{capec}) behind the flaw, the ATT\&CK techniques it enables~\cite{strom2018attack}, and the related mitigations, D3FEND countermeasures~\cite{d3fend}, and Sigma detections~\cite{sigma}. This analysis must then be combined with sensitive local context (asset inventory, scanner findings, exposure, business criticality) to plan the optimal risk response (patch now, apply a compensating control, or add detection until a maintenance window), a per-vulnerability analysis that NIST notes organizations lack the time and expertise to perform manually~\cite{nist80040r4}.

Each join maps free text into a controlled vocabulary, and near-misses are costly: a parent ATT\&CK technique in place of the sub-technique points detection engineering at the wrong telemetry; a related but incorrect CWE suggests the wrong compensating control; a wrong CVSS Attack Vector moves a vulnerability between remediation tiers; a misnormalized threat actor misdirects hunting; and an unparseable answer breaks downstream ticketing and orchestration. CTIBench~\cite{ctibench} and AthenaBench~\cite{athenabench} test models on exactly these mappings: CTI knowledge questions (CKT), attack-technique extraction from a threat description (ATE), root-cause mapping of a CVE to its CWE (RCM), risk-mitigation selection for a technique (RMS), vulnerability-severity prediction as a CVSS vector (VSP), and threat-actor attribution (TAA) (Section~\ref{sec:eval}).

That private context, which may include regulated data such as PHI and PII, along with licensed intelligence under sharing restrictions, is exactly what contractual, confidentiality, and data-residency obligations keep away from hosted large language model (LLM) APIs, frontier models included, favoring locally served open-weight models. Throughout, \emph{small language model} (SLM) is an operational term, not a parameter threshold: an open-weight model that an organization can fine-tune and serve on its own hardware, here on two 80-GB GPUs. The primary base model has 32B parameters, and we also test 8B, 14B, and sparse 30B (3B active) bases.

The standard way to specialize such a model is \emph{instruction fine-tuning} (IFT): continued supervised training on (instruction, input, output) \emph{triples}, so that the model learns to produce the output when given the instruction and input. Applying IFT to CTI raises two problems. First, the outputs must be correct and traceable: a recommendation that justifies an emergency change or a patch exception must lead back to a source record, yet triples synthesized by another language model are hard to trace to any source fact. Second, a model fine-tuned for several analyst tasks can lose one capability while gaining another, and a single final score hides such losses.

We address the first problem with two components. \emph{Ariadne} is a versioned Neo4j knowledge graph that merges the twelve public sources above into one typed schema. \emph{Sophia} generates IFT triples from expert-written templates: each template compiles to a graph query, and its placeholders are filled from the query's results, so every training target is derived from specific graph records rather than written by a language model. Private entities such as assets and scanner findings fit the same schema but are not used here. We address the second problem with \emph{layered IFT}: rather than one pass over a mixed corpus, the model is fine-tuned in four successive layers (catalog mapping, threat-actor attribution, SOC-style structured response, and recalibration), each starting from the previous layer's checkpoint, and every intermediate checkpoint is retained and evaluated.

Our contributions are: (i)~a graph-grounded data pipeline that produced a 219,675-row core training corpus in which every row resolves to its template, graph binding, and public source identifiers; (ii)~a layered IFT recipe that, applied to Qwen2.5-32B-Instruct, raises attack-technique extraction from 18.2 to 65.8 and mitigation selection from 7.6 to 62.5, lifting the three-benchmark mean from 57.7 to 65.0 (95\% interval 64.1--66.0), within 1.0 point of DeepSeek-V3.2-Exp, at a cost of 11.6 points on MMLU-Pro; against the single-stage first layer, the three later layers add 3.2 points to that mean but cost 2.3 on AthenaBench; (iii)~a checkpoint-level diagnosis of interference: the attribution layer raises canonical threat-actor attribution by 18.4 points, while the SOC-oriented layer raises CyberSOCEval malware accuracy by 19.7 points but erases 33.5 points of canonical attribution; and (iv)~an overlap audit at the 13-gram, entity, and complete-answer levels, extended after training to CyberSOCEval and the general instruction data, that finds little verbatim overlap and does not establish leakage as the explanation for the gains. The pipeline is released as Glaukopis~\cite{glaukopis}.

\section{Related Work}\label{sec:related}
\subsection{Instruction Fine-Tuning and Sequential Specialization}
IFT adapts a pretrained language model by continuing training on examples that pair a task instruction, and optionally an input, with the desired response; the loss is computed on the response tokens, so the model learns to produce the response given the instruction. FLAN showed that IFT on many instruction-formulated tasks transfers to unseen tasks~\cite{wei2022flan}; InstructGPT combined supervised demonstrations with preference-based training~\cite{ouyang2022training}; and later work studied how IFT scales with the number and mixture of tasks~\cite{chung2024scaling}. Continued training on domain text further improves domain tasks, motivating a separation between broad domain absorption and narrow task behavior~\cite{gururangan2020dont}. Fine-tuning one model sequentially on several datasets, however, exposes it to \emph{catastrophic interference}: learning a later task can overwrite behavior acquired earlier~\cite{mccloskey1989catastrophic}, and in a controlled comparison of mixed and sequential supervised fine-tuning, sequential training forgot earlier skills~\cite{dong2024composition}; a layered schedule must therefore be judged against a single-stage alternative. Layered IFT is a sequential schedule designed to make this interference observable rather than to eliminate it.

\subsection{Security Instruction Tuning}
CyberPal.AI's SecKnowledge pipeline combines expert-defined schemas, structure-driven generation, BRON graph paths, and LLM-augmented content generation~\cite{levi2025cyberpal}; follow-on work develops cybersecurity-expert SLMs with an enriched instruction pipeline using expert steering and LLM-driven multi-step grounding~\cite{levi2025slm}. SEvenLLM builds a bilingual CTI instruction corpus and benchmark~\cite{ji2024sevenllm}, and CyberBench pairs a multi-task cybersecurity benchmark with instruction-tuned CyberInstruct models~\cite{liu2024cyberbench}. These systems motivate domain-specific supervision, but none makes every training label the deterministic result of an executed graph query (Table~\ref{tab:related}).

\subsection{CTI Knowledge Graphs}
Open-CyKG constructs an open cyber-threat knowledge graph from unstructured reports~\cite{sarhan2021opencykg}. That work concerns how facts enter a graph; this work concerns how a populated graph is turned into IFT triples. The two qualities should not be conflated: a Sophia target is traceable to its graph binding, but the graph can still contain incomplete, stale, or misinterpreted source facts.

\section{Graph-Grounded Training Data}\label{sec:data}
\subsection{Formulation}
An IFT triple $r=(i,x,y)$ consists of an instruction $i$, an optional input or question $x$, and a target output $y$. Let $G_t=(V_t,E_t,A_t)$ be the Ariadne graph at snapshot $t$, with typed nodes $V_t$, typed relationships $E_t$, and node attributes $A_t$. A Sophia template $\tau$ is text with typed placeholders in its instruction, question, and answer parts $(i_\tau,x_\tau,y_\tau)$; it compiles to a graph query $q_\tau$ that includes any constraints the template declares. Executing the query returns a set of bindings $q_\tau(G_t)$, each binding $b$ assigning a node, relationship, or attribute value to every placeholder. For each binding $b\in q_\tau(G_t)$, Sophia emits one triple
\begin{equation}
 r_{\tau,b}=\big(\operatorname{render}(i_\tau,b),\,\operatorname{render}(x_\tau,b),\,\operatorname{render}(y_\tau,b)\big),
\end{equation}
where $\operatorname{render}(s,b)$ replaces each placeholder in text $s$ with its value under $b$. In short, a template generates one IFT triple per query result. Each row also records its template identifier and source tags, linking it to the template, snapshot, and public identifiers it was built from.

The fine-tuned model $p_\theta(y\mid i,x)$ is trained with the standard next-token cross-entropy on the target tokens. For layer $s$ with dataset $D_s$,
\begin{equation}
 \mathcal{L}_s(\theta)=-\sum_{(i,x,y)\in D_s}\sum_{j=1}^{|y|}\log p_\theta(y_j\mid i,x,y_{<j}),
\end{equation}
with the checkpoint from layer $s-1$ initializing layer $s$. No new optimizer, loss, or architecture is introduced; the method lies in how each $D_s$ is generated and in how the layers are sequenced.

\subsection{Ariadne: Graph Schema}
Ariadne is a Neo4j property graph built from the twelve public sources in Table~\ref{tab:schema}, grouped into seven layers. Each source contributes typed nodes keyed by their natural identifiers (STIX, CVE, CWE, CAPEC, or D3FEND IDs). Ingestion uses Neo4j \texttt{MERGE} operations under uniqueness constraints on those keys, so re-running it never duplicates nodes, and it follows dependency order---framework catalogs, then vulnerabilities, then exploit evidence---so every cross-framework relationship has both endpoints present. The relationships most used by templates form a spine from vulnerability to weakness to attack pattern to adversary technique, with mitigations, countermeasures, and detections attached to techniques and exploitation signals attached to vulnerabilities. The snapshot used here holds 214,651 nodes with 31 labels and 330,935 relationships of 41 types. Bounded catalogs are loaded in full; the high-churn vulnerability and exploit feeds are scoped to 2024 onward. EPSS and the current-year NVD feed are refreshed daily and other sources on explicit refresh, so dataset freshness is tracked per source.

\subsection{Sophia: Template-Driven Triple Generation}
A Sophia template is plain text with placeholders in braces. A placeholder \texttt{\{a:Label.prop\}} binds alias \texttt{a} to a node of type \texttt{Label} and inserts its property \texttt{prop}; \texttt{\{a.rel>Label.prop\}} follows relationship \texttt{rel} from the node bound to \texttt{a}; and \texttt{\{a.prop\}} reuses an existing binding. Hidden sections \texttt{<*\{\ldots\}*>} add bindings or constraints to the query without producing text. The language also supports any/all filters over list-valued properties, list expansion, and source prefixes that distinguish same-named types such as ATT\&CK and CAPEC attack patterns. A simple template binds one ATT\&CK technique and emits its properties:
\begin{quote}\scriptsize\ttfamily\sloppy
Question: Explain ATT\&CK technique \{ap:attack-pattern.name\} (\{ap.id\}) and how it is used.\\
Answer: Technique \{ap.name\} (\{ap.id\}) is described as: \{ap.description\}. Commonly observed across \{ap.x\_mitre\_platforms\}.
\end{quote}
Executed against Ariadne, this template yields one triple per technique node. Templates become more useful when they traverse relationships across frameworks. The following template from the generator's library correlates a CVE with its attack pattern and weakness:
\begin{quote}\scriptsize\ttfamily\sloppy
Instruction: You are a cybersecurity expert that has been trained to give precise responses to complex cybersecurity questions. You work in a SOC protecting data for enterprise customers helping to protect their digital assets.\\
Question: Correlate CVE, CWE, and CAPEC for a single vulnerability chain.\\
Answer: CVE \{cve:CVE.id\} impacts CAPEC \{cap:cve.impacts>CAPEC.name\} and is categorized as weakness \{cwe:cve.problemType>Weakness.name\}. CAPEC \{cap.id\} exploits weakness \{cwe2:cap.exploits>Weakness.name\}. <*\{force cwe.id=cwe2.id\}*>
\end{quote}
The template compiler turns each binding into a \texttt{MATCH} pattern of a Cypher query and the hidden \texttt{force} section into a \texttt{WHERE} condition, schematically:
\begin{quote}\scriptsize\ttfamily
MATCH (cve:CVE)-[:impacts]->(cap:CAPEC),\\
\hspace*{1em}(cve)-[:problemType]->(cwe:Weakness),\\
\hspace*{1em}(cap)-[:exploits]->(cwe2:Weakness)\\
WHERE cwe.id = cwe2.id RETURN cve, cap, cwe, cwe2
\end{quote}
Only chains in which the CVE's own weakness is also the weakness the attack pattern exploits are returned, and each returned row is rendered into one triple whose answer names the CVE, the attack pattern, and the weakness. Any generated answer can therefore be checked by re-running its query. Negative examples use inequality constraints; because CTI graphs are incomplete, such examples mean ``not supported by the graph'' rather than ``false in the world.''

Generation runs in three steps: templates are extracted from their authoring documents; each is executed against Ariadne, producing its triples and a report of failed or empty queries; and the results are merged into one dataset. Rows are then balanced across template families, deduplicated, screened for overlap with evaluation data (Section~\ref{sec:overlap}), license-gated, and serialized as JSON. Schema tests catch templates that reference absent node types, relationships, or properties, but they do not replace expert review of whether a template's mapping is semantically right: Sophia guarantees a deterministic path from query to target, not the correctness of every upstream fact.

\subsection{Training Corpus}
A \emph{shard} is the set of triples generated for one training layer. The build produced four training shards and three validation shards, the latter holding out 50 rows per template family. The core corpus contained 219,675 rows after balancing; after the overlap screen removed 684 rows, 550 were held out for validation, and one training row identical to a validation row was dropped, it was split into Core-A (168,859 rows: knowledge, multiple-choice, mitigation, attribution, and SOC families) and Core-B (49,581 rows: drills for the RMS, ATE, VSP, and RCM tasks of Table~\ref{tab:eval}). The TAA (attribution) and CSE (SOC-style response) shards contain 20,359 and 17,320 rows. Core-A is mixed with general-purpose instruction data to limit loss of general ability: the first 240,000 rows of the T\"ulu-3 SFT mixture~\cite{lambert2024tulu} (239,985 usable conversations) and the 999-row Alpaca demonstration set~\cite{taori2023alpaca}. These auxiliary examples are not generated by Sophia.

Each layer targets one analyst role, and its checkpoint is retained so that both its gains and any damage to earlier skills can be measured. \textbf{Layer 1 (Core): catalog mapping.} Phase~1A trains on Core-A plus the general instruction data to establish broad CTI knowledge. Phase~1B then trains on Core-B at a lower learning rate with longer, unpacked sequences, so that long structured answers such as CVSS vectors and mitigation lists are learned exactly. (\emph{Packing} concatenates short examples into one training sequence for efficiency; it is disabled where answers must not be split.)

\textbf{Layer 2 (+TAA): attribution.} Drills that map threat-report descriptions to ATT\&CK groups.

\textbf{Layer 3 (CSE): SOC-style response.} Drills in the multiple-answer, letter-set format used by CyberSOCEval's malware and threat-intelligence tasks.

\textbf{Layer 4 (Recal): recalibration.} A short pass at a low learning rate that interleaves samples from Core-A, Core-B, and TAA to recover skills disturbed by Layers~2--3.

Ordering from broad catalog knowledge to narrow role-specific behavior lets each layer build on the last, and because each layer consumes a known shard, a regression can be localized to the layer that caused it and addressed by retraining only that layer and its successors.

The base model is Qwen2.5-32B-Instruct~\cite{qwen25}, trained with LlamaFactory~\cite{zheng2024llamafactory} and DeepSpeed ZeRO-3~\cite{rajbhandari2020zero} in bfloat16 with an 8-bit AdamW optimizer on eight 80-GB H100 GPUs. Table~\ref{tab:train} lists per-layer settings. Each shard is consumed in one epoch; Table~\ref{tab:train} gives the examples and tokens each pass consumed. In Phase~1A the 240,000-row sample cap applies to each dataset separately: it truncates T\"ulu-3 to its first 240,000 rows and leaves Core-A and Alpaca whole, so general data supply 87\% of the pass's 314.9M tokens. Layer~4 interleaves about 6,000 examples. Its recipe is model-specific: a lower-learning-rate, more balanced setting that recovered VSP on a 14B base drifted VSP the wrong way at 32B, so the 32B recipe in Table~\ref{tab:train} weights Core-B more heavily; both variants were trained from the same 32B Layer-3 parent for comparison. We also apply the recipe to four other base models (Section~\ref{sec:ports}); the 14B transfer uses the alternative Layer-4 setting (learning rate $10^{-6}$, mixture 0.25/0.40/0.35, 2,400 examples).

\section{Evaluation Setup}\label{sec:eval}
AthenaBench contains six task families, each corresponding to one analyst step from Section~I (Table~\ref{tab:eval}). A correct RCM answer identifies the weakness class and hence the relevant compensating controls; a correct VSP vector sets remediation priority; and correct ATE and RMS answers direct detection and mitigation work. TAA appears in a lenient \emph{Classic} form and a strict \emph{Canonical} form that requires the group's canonical name or ATT\&CK G-code. We also evaluate on CyberSOCEval (malware analysis and threat-intelligence reasoning with multiple-answer questions)~\cite{deason2025cybersoceval}, CyberMetric (cybersecurity multiple-choice questions in 2K and 10K tiers)~\cite{tihanyi2024cybermetric}, and MMLU-Pro, a general-knowledge benchmark used here to measure forgetting~\cite{wang2024mmlupro}.

CKT, RCM, CyberMetric, and MMLU-Pro use exact matching, and ATE credits the parent technique. VSP converts predicted and gold vectors to CVSS v3.1 base scores~\cite{first2019cvss} and scores their normalized distance; two of 2,000 final-checkpoint vectors are unparseable and excluded. RMS uses set F1, with half credit for mitigations in the target technique's neighborhood. TAA Classic gives full credit to an alias of the correct group and half credit to a related group; TAA Canonical gives full credit to the canonical name or G-code and half credit to another alias. CyberSOCEval reports strict accuracy and Jaccard similarity over answer-letter sets. These scores differ in kind (Table~\ref{tab:eval} marks each as an accuracy, an F1, or a partial-credit score) and are not calibrated probabilities. Checkpoints are served with vLLM~\cite{kwon2023vllm}, and each score is one evaluation of one training run.

To keep Canonical TAA visible, we average the two TAA forms and define two aggregates:
\begin{equation}
T_{bal}=\tfrac{1}{2}(T_{Classic}+T_{Canonical}),
\end{equation}
\begin{equation}
A_{bal}=\tfrac{1}{6}(K+E+R+M+V+T_{bal}),
\end{equation}
\begin{equation}
B_{bal}=\tfrac{1}{3}(A_{bal}+C+Y),
\end{equation}
where $K,E,R,M,V$ denote CKT, ATE, RCM, RMS, and VSP; $Y$ is the mean of the CyberMetric tiers; and $C$ is the CyberSOCEval composite (mean of malware strict accuracy, malware Jaccard, and threat-intelligence strict accuracy). $T_{bal}$, $A_{bal}$, and $B_{bal}$ are composite averages of these heterogeneous scores, not accuracies; $B_{bal}$ is the three-benchmark mean reported throughout.

For the five fine-tuned checkpoints, 95\% percentile bootstrap intervals use 2,000 item-resampling replicates~\cite{efron1993bootstrap}; differences between checkpoints resample the same items for both, giving paired estimates. The intervals capture item-sampling uncertainty for fixed checkpoints, not training-seed variance. Item-level files were unavailable for the base and hosted models, so paired statistics involving them are not reported.

\section{Training--Evaluation Overlap}\label{sec:overlap}
Because training and evaluation draw on the same public catalogs, we audit overlap at two levels.

\textbf{Verbatim screen.} Before training, every generated row was compared with the locally available evaluation files for shared 13-grams---runs of 13 consecutive lowercased words, the window used in the GPT-3 contamination audit~\cite{brown2020language}. Rows sharing at least 50 distinct 13-grams with one evaluation item were removed; rows sharing fewer were flagged (Table~\ref{tab:contam}). CyberSOCEval files were not present when the CSE shard was built, and the general datasets were not screened, so after training we closed both gaps with the same rule. Against the 1,197 CyberSOCEval questions and their options, no Core or TAA row and 86 of the 17,320 CSE rows share any 13-gram, none more than four. Against AthenaBench, CyberMetric, and CyberSOCEval together, 22 of the 240,000 T\"ulu-3 rows (none more than twelve) and one of the 999 Alpaca rows do. No row in either screen reaches the removal threshold. This remains a verbatim screen: it cannot detect paraphrase.

\subsection{Layered versus Single-Stage Training}\label{sec:singlestage}
The Core checkpoint is the model that single-stage fine-tuning on the core shards produces: Layer~1 trains the base once, without the attribution, SOC-format, or recalibration layers, and Core is evaluated with the same harness and per-item records as every later checkpoint. Against it, with paired intervals (Table~\ref{tab:transitions}, last column), the three later layers add 3.2 points to $B_{bal}$ [2.2, 4.2] through CyberSOCEval malware (+18.6) and threat-intelligence (+7.9) accuracy and CKT (+2.7), and remove 2.3 points from $A_{bal}$, 15.0 from Canonical TAA, 5.3 from VSP, 2.7 from RCM, and 1.8 from MMLU-Pro. Layering is therefore a trade rather than a uniform improvement. Because the later layers also add the attribution and SOC-format shards, this comparison does not separate the value of that data from the value of training on it in separate layers; a single pass over all four shards with matched tokens and a chain that omits the attribution layer would isolate the two, and were not run for this paper.

\section{Discussion}\label{sec:discussion}
\subsection{Implications for Cybersecurity SLM Design}
Graph-grounded generation and layered IFT address different failure surfaces. Ariadne and Sophia act on supervision: they make the origin of each target inspectable and let coverage be designed around explicit CTI schemas. Retained checkpoints act on optimization: they reveal how later specialization changes behavior earlier layers had acquired. The graph path is directly auditable; against the single-stage first layer, the four-layer order trades aligned accuracy for SOC-format competence (Section~\ref{sec:singlestage}).

For SLMs, limited capacity and aggressive specialization create a tension between narrow competence and general capability. The 32B chain gains strongly on schema-aligned tasks while losing MMLU-Pro, and the 8B transfers show that a recipe that works on a larger base can fail on a smaller one. An SLM is therefore better treated as a bounded specialist whose accepted task types are defined by measured competence, with broader reasoning routed elsewhere.

The transitions also argue for keeping intermediate checkpoints: +TAA is materially better at canonical attribution than later checkpoints, while CSE improves SOC-style tasks. A single sequence can thus move the model between capability profiles rather than improving one objective monotonically. Retained checkpoints let a deployment select the checkpoint that matches its role.

\subsection{Limitations and Operational Boundaries}\label{sec:limits}
\textbf{Scope.} The tasks evaluated are the individual mapping steps that feed a risk assessment and mitigation plan. We do not evaluate a complete patch plan produced for a real organization's assets and scan data, and no private data was used.

\textbf{Benchmark alignment.} Training deliberately targets AthenaBench's task formats, and one author co-developed that benchmark. The overlap audit does not establish leakage as the explanation for the gains, but public-catalog overlap, shared answer spaces, paraphrase, and benchmark-guided recipe development limit out-of-sample claims. The final checkpoint does not improve CyberSOCEval and lowers MMLU-Pro. An entity-disjoint or temporally held-out incident set, evaluated once after checkpoint selection on separate development data, is needed for a strong generalization claim.

\textbf{Causal attribution.} Graph-derived data, shard composition, training length, order, sequence length, packing, and learning rate co-vary across layers, so the retained checkpoints show observed transitions, not causal effects. The Core checkpoint provides a single-stage baseline (Section~\ref{sec:singlestage}), but a one-pass mixture over all four shards with matched tokens and a Core$\rightarrow$CSE chain that omits attribution were not run, and the label ``final'' denotes the released checkpoint, not an established optimum.

\textbf{Uncertainty and reproducibility.} Intervals cover item sampling, not training-seed variance: every checkpoint is one training run, and seeded replication of Layer~4 and of the full chain would test recipe robustness.

Row-level regeneration was not fully seed-pinned (graph-read order and deduplication tie-breaks can vary), so exact replay requires preserving the graph snapshot, serialized shards, and seeds together.

\textbf{Operational safety.} Graph-grounded training does not guarantee graph-faithful answers at inference time; retrieval, constrained decoding, output verification, and human approval are separate mechanisms. The Canonical-TAA collapse and the VSP reachability errors show that the model should not be the sole basis for attribution or prioritization decisions. Prompt-injection resistance, private-telemetry performance, latency under load, and analyst utility were not established.

\section{Conclusion and Future Work}
This paper asked whether a locally served SLM can be specialized for the catalog mappings of vulnerability response without giving up the traceability that security decisions require, and without hiding what specialization costs.

Our answer has four parts. First, Ariadne and Sophia show that IFT data for CTI can be generated without a language model writing the targets: Ariadne merges twelve public sources into a typed graph of 214,651 nodes and 330,935 relationships, and Sophia compiles expert-written templates into graph queries whose results are rendered into triples, producing a 219,675-row core corpus in which every target traces to a template, a graph binding, and public identifiers. Second, layered IFT on Qwen2.5-32B-Instruct turns this data into large gains on the mappings that matter most operationally: attack-technique extraction rises from 18.2 to 65.8 and mitigation selection from 7.6 to 62.5, and the three-benchmark mean reaches 65.0, within a point of DeepSeek-V3.2-Exp and above Gemini-2.5-Flash, from a model served on a two-GPU host. Third, retaining every checkpoint turns interference from an invisible side effect into a measured quantity: the attribution layer adds 18.4 points of canonical attribution that the SOC-oriented layer then erases through wrong but well-formed group names, and the same layer shifts CVSS errors into Attack Vector, Privileges Required, and Scope. Fourth, the overlap audit, extended after training to CyberSOCEval and the general instruction data, finds little verbatim overlap and does not establish leakage as the explanation for the mapping gains.

Three practical lessons follow. Provenance can be designed into training data rather than reconstructed afterwards: when the model learns a wrong mapping, the template and query that taught it can be inspected and corrected. A specialized SLM is best deployed as a bounded specialist for validated task types, with its MMLU-Pro loss treated as a signal to route broader reasoning elsewhere. And a fine-tuning schedule should be evaluated layer by layer, because the checkpoint that is best for one analyst role---here, +TAA for attribution---need not be the final one.

Future work follows directly from these results: one-pass training on all four shards with matched tokens, a chain that omits attribution, and seeded replications, to separate the effect of layering from that of the added data; temporally held-out evaluation, in which a frozen Ariadne snapshot trains a model that is tested on CVEs, techniques, and campaigns that appear only in later snapshots, paired with embedding-based screening for paraphrase; replay mixtures that recover canonical attribution and the CVSS reachability fields without surrendering the CyberSOCEval gain; organization-specific training data generated inside the security boundary from assets, scanner findings, and tickets; verifiable rewards computed by re-executing Sophia queries; and deployment studies that route task families to the checkpoint best suited to them and measure analyst utility, latency, and prompt-injection resistance.

More broadly, a specialized security model is only as trustworthy as the path from its training data back to the source. Making that path explicit, and measuring what each step of specialization gains and loses, is what allows such a model to be deployed with bounded and documented risk.
